# Monet

A local-first Markdown vault for macOS with a 3D link graph — and a command
line interface that speaks to the very same folder of files.

Monet is a functional clone of Obsidian: notes are plain `.md` files, links
are `[[wikilinks]]`, backlinks are indexed automatically, and the whole vault
is rendered as an explorable 3D graph.

```
monet/
├── MonetApp/          SwiftUI application (macOS 26+, Liquid Glass)
├── MonetCore/         Vault engine: parser, index, search, watcher, layout
├── packages/cli/      TypeScript CLI + MCP server, built with Incur
├── MonetSkill/        The authored skill template (en, pt-BR, es)
├── Fixtures/          The fixture shared by the Swift and TypeScript tests
└── ExampleVault/      A 60 note vault generated by the seed script
```

## What it does

| | |
|---|---|
| **Vault** | Notes are Markdown files in a folder. YAML frontmatter, `[[wikilinks]]`, `![[embeds]]`, `#tags` and aliases. Link resolution matches Obsidian: no extension, case-insensitive, aliases, and duplicate titles resolve to the closest file. Backlinks, tags, search, history and favourites are all indexed automatically. |
| **Graph** | The whole vault as a 3D scene: nodes are notes, edges are links. Free camera (orbit, pan, zoom), node picking, neighbour highlighting, tag filtering and a stable 3D force-directed layout. The same layout runs in the app and in the CLI. |
| **Liquid Glass** | Every surface — sidebars, toolbars, popovers, the workspace switcher, the inspector — uses Apple's native `glassEffect` API on macOS 26 (Tahoe). |
| **Multi-language** | A native String Catalog with English, Brazilian Portuguese and Spanish. The CLI ships the same three locales for its help, its errors and the skill. |
| **CLI** | One declaration per command generates the terminal CLI, the MCP server, the `--llms` manifest, the `--schema` output and the shell completions. |
| **Agents** | `monet skills add` installs the skills into Claude Code, Cursor, Codex, OpenCode and every other agent incur knows about. `monet mcp add` registers the CLI as an MCP server. |

## Build and run

### The application

```sh
# Build and run straight from the package.
swift build
swift run MonetApp

# Or assemble a double clickable .app bundle.
scripts/build-app.sh
open build/Monet.app
```

The bundle is signed ad-hoc, so macOS Gatekeeper asks for a confirmation the
first time you open it. The app accepts a vault folder as its first argument:

```sh
open build/Monet.app --args "$PWD/ExampleVault"
```

### Screenshots

```sh
scripts/screenshot.sh
```

The app renders its own window into a PNG (`Monet --capture`), so the
screenshots do not need the Screen Recording permission. The capture mode
draws the translucent surfaces as solid colours, because the offscreen
renderer cannot rasterise a system material; the layout, the typography and
the colours are identical to the running app.

### The example vault

```sh
pnpm seed
# or: pnpm --filter @monet/cli seed ExampleVault --notes 60
```

The vault lands in `ExampleVault/` at the root of the repository. It holds
60 notes and more than a hundred wikilinks.

The seed script is deterministic: the same seed always produces the same
notes, links and tags, so the screenshots and the tests always match.

### The command line interface

```sh
pnpm install
pnpm --filter @monet/cli build

# Run it from the sources.
pnpm --filter @monet/cli dev -- note list --vault ../ExampleVault

# Or use the compiled entry point.
node packages/cli/dist/bin.js --help
```

### The standalone binaries

```sh
pnpm --filter @monet/cli build:binary
```

`incur build` produces self-contained executables for macOS, Linux and
Windows (arm64 and x64), a `SHA256SUMS` file and the `install.sh` /
`install.ps1` installers, in `packages/cli/dist/binaries/`.

The release is automated in
[`.github/workflows/binary-release.yml`](.github/workflows/binary-release.yml):
push a `v*` tag and the workflow builds the binaries, copies the skill
template next to them and publishes the release with
[`wevm/incur/release`](https://github.com/wevm/incur).

## The vault format

A vault is an ordinary folder. Monet never rewrites a file it did not have to
touch, and everything it does write is plain Markdown.

```markdown
---
title: Release Plan
tags: [project, release]
aliases: [Plan]
---

# Release Plan

The release ships on Friday. See [[Design Notes]] and ![[Checklist]].

Tagged #project and #area/product.
```

- **Wikilinks** — `[[Note]]`, `[[Note|display text]]`, `[[Note#Section]]`.
- **Embeds** — `![[Note]]`.
- **Tags** — `#tag`, `#nested/tag`, or a `tags` list in the frontmatter.
- **Aliases** — `alias` or `aliases` in the frontmatter.

Links inside fenced code blocks and inline code spans are ignored, exactly
like in Obsidian.

### Link resolution

| Written | Resolves to |
|---|---|
| `[[Note]]` | the note whose file name is `Note` |
| `[[Note.md]]` | the same note — the extension is optional |
| `[[note]]` | the same note — matching is case-insensitive |
| `[[Folder/Note]]` | the note at that path |
| `[[Alias]]` | the note that declares that alias |
| `[[#Section]]` | a section of the note the link appears in |

When several notes share a file name, the one in the closest folder wins;
ties are broken by the shortest path and then alphabetically, so the result
is always the same on every machine.

## The application

- **Sidebar** — the folder tree, the tag list and the favourites, with a
  fuzzy search field at the top.
- **Editor** — a native `NSTextView` with Markdown highlighting, wikilink
  autocompletion (`[[` opens a list of matching notes) and a dirty-state
  aware save button.
- **Inspector** — backlinks, outgoing links, the outline and the metadata of
  the current note.
- **Graph** — the vault in 3D. Drag to orbit, scroll to zoom, shift-drag to
  pan. Click a node to select it; its neighbours light up and the inspector
  follows along. The filter menu narrows the graph to a single tag.
- **Shortcuts** — `⌘O` opens a vault, `⌘N` creates a note, `⌘S` saves,
  `⌘R` reloads, `⌥⌘I` toggles the inspector.

The app also takes the vault — and optionally the note to show — as its
arguments, which is how `monet open` reaches it:

```sh
Monet.app/Contents/MacOS/Monet ~/Documents/MyVault "Projects/Plan"
```

Favourites and the note history are per-user state and live in Application
Support, never inside the vault, so the app and the CLI can never disagree
about the contents of a vault.

## The command line interface

```sh
monet note new "Release Plan" --folder Projects --tag project
monet note list --tag project
monet note show "Release Plan" --links
monet note edit "Release Plan" --append "Ship on Friday."
monet note move "Release Plan" --to "Archive/2026/Release Plan"
monet note delete "Release Plan" --yes

monet search "release" --limit 20
monet link create "Checklist" --target "Design Notes"
monet link check "Checklist" --target "Design Notes"
monet backlinks "Design Notes"
monet graph --format json
monet tags
monet config set --vault ~/Documents/MyVault
monet open
```

### Output formats

Every command accepts `--format toon|json|yaml|md|jsonl`. The default is
TOON, which is compact and easy for an agent to read; `--format json` is for
programs.

```sh
monet graph --format json | jq '.nodes | length'
```

### The vault the CLI uses

The vault is resolved from, in order: the `--vault` flag, the `MONET_VAULT`
environment variable, the `monet config set --vault` setting, and finally the
current directory.

### Concurrent editing

When the Monet app has the same vault open, the CLI notices. The app
publishes a lock file in Application Support; the CLI checks that the
process is still alive and warns before it writes. The CLI never blocks —
it only tells you that both sides may touch the same file.

## The MCP server

The same command definitions that build the terminal CLI build the MCP
server, so an agent can call every command as a tool.

```sh
monet --mcp            # stdio server
monet mcp add          # register the CLI with Claude Code, Cursor, Amp, …
```

Over HTTP the same server is reachable at `POST /mcp`.

The tool names are the command names with the group prefix: `note_new`,
`note_list`, `note_show`, `search`, `backlinks`, `graph`, `tags`, `link_create`,
`link_check`, `open`.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "query": "release", "vault": "/Users/me/MyVault" }
  }
}
```

## Agent skills

```sh
monet skills add     # install the skills into every detected agent
monet skills list    # show what is installed
monet mcp add        # register the CLI as an MCP server
```

`monet skills add` uses incur's own skill synchronisation, so there is no
manual configuration: the skills land in the canonical
`~/.agents/skills/<name>` folder and are symlinked into the folder of every
agent that is installed on the machine — Claude Code, Cursor, Codex, OpenCode,
Amp, Cline, Gemini CLI, GitHub Copilot, Windsurf, Continue, Roo and more.

Two kinds of skill are installed:

- **`monet-<command>`** — the generated command reference for each group of
  commands (`monet-note`, `monet-search`, `monet-graph`, …), generated from
  the command definitions.
- **`monet`** — the authored skill in [`MonetSkill/SKILL.md`](MonetSkill/SKILL.md):
  a guide to the vault format, how to open a vault, create notes, connect
  them, read the graph, and worked examples of every tool call. It is a
  versioned template in the repository, never a string baked into the code,
  and it ships in English, Brazilian Portuguese and Spanish.

The authored template is included through incur's `sync.include` mechanism,
so it is installed by exactly the same code path as the generated skills.

## Tests

```sh
# The Swift engine.
swift build && swift test

# The CLI, the MCP contract and the parser parity.
pnpm install
pnpm test
```

The two implementations of the vault format are kept honest by a **shared
fixture**: `Fixtures/parity.md` is parsed by the Swift engine
(`MonetCore/Tests/MonetCoreTests/ParityTests.swift`) and by the TypeScript
engine (`packages/cli/test/parity.test.ts`), and both are compared with
`Fixtures/parity.json`. A change to one parser that is not mirrored in the
other fails a test.

| Suite | What it covers |
|---|---|
| `WikilinkParserTests` | links, embeds, aliases, headings, tags, code blocks |
| `LinkResolverTests` | Obsidian-compatible resolution, duplicate titles, aliases |
| `BacklinkIndexTests` | the index, backlinks, tags, the folder tree, round trips |
| `SearchEngineTests` | the ranking, the fuzzy matching, the filters |
| `FrontmatterAndGraphTests` | the YAML subset, the 3D layout |
| `ParityTests` | the Swift/TypeScript contract |
| `MarkdownHighlighterTests` | the editor highlighting, including the empty case |
| `GraphSceneTests` | the 3D scene, the buckets and the picking |
| `wikilink.test.ts` | the TypeScript parser |
| `vault.test.ts` | the TypeScript index, backlinks, resolution |
| `search.test.ts` | the TypeScript ranking |
| `cli.test.ts` | the commands, `--llms`, `--schema`, completions |
| `mcp-contract.test.ts` | `initialize`, `tools/list` and a real `tools/call` |
| `parity.test.ts` | the Swift/TypeScript contract |

## Design notes

### Liquid Glass, used where it belongs

The Apple Human Interface Guidelines are explicit about Liquid Glass: it is
the material of the **navigation layer** that floats above content, it is
never used inside the content layer, and it is never stacked on itself. The
window follows that rule literally.

| Surface | Material | Why |
|---|---|---|
| Window toolbar | Liquid Glass (system) | macOS 26 draws the toolbar as glass automatically; the app adds no second layer on top of it. |
| Sidebar | `.regularMaterial` (system) | A content-layer surface. The HIG asks for standard materials here, not glass. |
| Note list | Solid `controlBackgroundColor` | Dense, readable content. |
| Editor | Solid `textBackgroundColor` | The reading surface. Glass would hurt legibility. |
| Inspector | `.regularMaterial` (system) | A content-layer surface, like the sidebar. |
| Graph controls | **Liquid Glass** (`glassEffect`) | Custom controls floating above a 3D canvas — the case the material is designed for. |
| Command palette | `.thickMaterial` | A floating panel that holds a list, so it needs the readability of a material. |

The graph controls are the one place where the app applies glass by hand, and
they are built the way the guidelines require:

```swift
GlassEffectContainer(spacing: 10) {
  HStack(spacing: 10) {
    stats.glassEffect(.regular, in: Capsule())
           .glassEffectID("stats", in: namespace)

    Button { … }.glassEffect(.regular.interactive(), in: Circle())
                .glassEffectID("relayout", in: namespace)
  }
}
```

- Everything sits inside a single **`GlassEffectContainer`**, so the shapes
  blend and morph into one another instead of stacking. Glass cannot sample
  glass, and a container is how the system avoids that.
- The buttons use `.interactive()`, which gives them the pointer response the
  material expects.
- `.regular` is used everywhere. `.clear` is reserved for controls that sit
  over visually rich media and need the content to show through; the app does
  not have such a surface in this release, so it is not used. The variant
  exists in `LiquidGlass.swift` and is documented as the media case.
- Every shape carries a `glassEffectID`, so the legend panel materialises and
  dematerialises with `glassEffectTransition(.materialize)` instead of popping.

#### The fallback

`LiquidGlass.swift` wraps the effect:

```swift
content.glassEffect(glass, in: AnyGlassShape(shape))
```

The availability check is a **runtime** check rather than an `#available`
guard: `#available` is folded away by the compiler when the deployment target
already contains the API, and the fallback branch would become unreachable
code that can never be exercised. When the native API is unavailable the view
falls back to `.ultraThinMaterial`, which is what the system itself renders
when a glass material is unavailable. `LiquidGlass.fallbackReason` carries the
reason so it can be surfaced in diagnostics.

### The 3D graph

SceneKit's `SCNInstancingGeometry` was **removed from the public macOS 26
SDK**, so Monet does not use it. Instead:

- Every node mesh is merged into a single `SCNGeometry` with **one element
  per colour bucket**, and every edge is merged into a single line geometry.
  A vault with two thousand notes is drawn in roughly ten draw calls.
- Picking uses `SCNHitTestResult.geometryIndex` (the colour bucket) and
  `faceIndex` (the triangle), which map straight back to a note id.
- The level-of-detail strategy is the mesh itself: the bulk of the graph uses
  a 20 triangle icosahedron, and only the selected node and its neighbours
  are promoted to the subdivided mesh.

The layout itself lives in `MonetCore` and is deterministic: the starting
positions come from a stable hash of the note id, so the same vault always
produces the same graph — in the app and in the CLI.

### One vault, two implementations

The app and the CLI read and write the same files. The only duplicated
knowledge is the *parser*, and the shared parity fixture keeps the two
implementations honest. Everything else — favourites, history, the window
layout — is per-user state that lives outside the vault.
